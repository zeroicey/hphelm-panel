# 面板「变慢」的量法错了：在别人满载的机器上量 CPU

**状态：** ✅ 已解决（2026-10-21）

## 症状

给面板加第二台主机（生产服务器）之后，`tools/deploy.sh` 报：

```
! CPU=1.33% of one core（预算 <1%）
```

同一天早些时候我在 Xvfb 里量到 1.17% / 1.50% / 1.03% / 0.77% / 1.60% —— 同一份代码、
同样的负载，数字在 0.77%~1.60% 之间乱跳。我据此做了三轮「优化」，还写了一个 A/B 对照脚本
（旧二进制 vs 新二进制各 20 秒），结果对照表是这样的：

```
round 1: 旧版(1台)=1.15%  新版(2台)=1.90%
round 2: 旧版(1台)=2.20%  新版(2台)=1.35%
round 3: 旧版(1台)=1.75%  新版(2台)=2.25%
```

旧版比新版还慢、同一版本两轮差一倍 —— **这个对照表本身就在报警**，我却继续在代码里找原因。

## 根因

`uptime` 一看就明白了：

```
 17:22:05 up 3 days,  3:09,  5 users,  load average: 22.99, 10.19, 4.54
```

当时这台机上**正在跑无关的 `go install`（编译整棵 nuclei/katana 依赖树）**，8 核机的
load average 冲到 23。面板的 CPU 时间片被挤、cairo/pango 的缓存被换出，测出来的数字
是「机器有多忙」，不是「面板有多贵」。

## 修法（判据本身要改）

1. **量 CPU 必须同时记录 load average**，并把窗口拉到 ≥20 秒：
   ```sh
   uptime                       # load > nproc/2 就别量了
   pid=$(pgrep -x hphelm-panel)
   a=$(awk '{print $14+$15}' /proc/$pid/stat); sleep 20
   b=$(awk '{print $14+$15}' /proc/$pid/stat)
   # jiffies × 10ms / 窗口 ms × 100
   ```
2. **A/B 对照要做「同一窗口内交替」**，不能串行跑两轮 —— 串行的两轮之间负载会漂移。
   正确形状：`A(10s) B(10s) A(10s) B(10s)`，取各自的中位数。
3. **先看 `HPHELM_PANEL_DEBUG=1` 的单帧耗时**再谈优化。本轮真实的数字是
   「签名 0.1ms / 绘制 5~10ms / 上屏 0.0~0.1ms」—— 单帧 × 1 Hz 就解释了全部 CPU，
   于是优化方向（pango 整形次数、整屏渐变填充）是明确的，不用猜。

## 顺带量出来的两个真问题（已修，不是噪声）

| 大头 | 证据 | 修法 |
| --- | --- | --- |
| pango 整形 100+ 次/帧 | 右对齐是「先 `v_text_w()` 量、再 `v_text()` 排」⇒ 每次两遍 | `v_text_right_w()` 复用同一次排版 |
| 整屏渐变每帧重算 | 把渐变换成纯色后单帧从 11ms 掉到 5~9ms | 渐变渲染进 `bgpix`，每帧一次 `XCopyArea` |

## 给下一轮的判据

- [ ] 报 CPU 时必须写清：**窗口长度、load average、是否只本机**（含/不含 `--remote`）
- [ ] 任何「优化前后」的数字，必须在同一窗口内交替量，否则不许下结论
- [ ] 看到同一份代码的数字波动 > 50% ⇒ **先怀疑环境**，别先怀疑代码
